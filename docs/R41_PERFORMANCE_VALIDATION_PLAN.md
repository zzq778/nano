# r41 性能验证与发布门槛（待 Jetson 实机执行）

本文件是**测试准备与验收标准**，不是 r41 已在 Jetson 达到该指标的声明。所有本机结果和硬件结果分开记录。2026-11-22 冻结的生产约束：Astra 640×480 RGB888、六类 YOLO、STM32 USART3 230400、每帧物块典型约 15 个/最多 32 个条目、5–6 Hz 输出目标。不更改 UART 字段、设备标定、模型权重、默认阈值及生产 `.so`。

## 1. 执行原则

- **现在不执行**任何 Jetson、相机、串口或系统管理命令。所有脚本均已准备，并可先在本机运行。
- Git 开发代理仅使用独立工作区；从受审查的 `chat/*` 分支按 **40 位提交 SHA** 拉取，不接受自由 Shell；只有经过本地单测的版本才能更新 Nano 上的代理。
- 每轮测试保存：代码 SHA、相机/模型/标定身份、供电/功率模式、风扇设置、频率/温度、Python/OpenCV/TensorRT 版本、实际帧数、测试输入和输出。缺任何关键条件时，结果只能用于诊断，不用于前后性能结论。
- **不同时启动第二个 Astra 采集进程**。测试真实相机前需明确选择停止或接管生产程序；不自动打开 `/dev/tty*`，默认测试用 PTY/loopback。
- `r41` 的已打包 ARM64 `.so` 仍为原版本，因此只有重新编译并验证后的原生库才能代表 r41 C++ 优化。
- 代码安全检查的“通过”和生产系统“已验证”不同；无测试数据或缺 SDK 时要明确标记 `SKIP`，不能用空结果冒充通过。

## 3. 统计定义和报告规则

- **P50**：中位数；**P95/P99**：耗时尾部第 95/99 百分位（最近秩）；`mean`、`max`、样本数同时呈现。小于 100 帧时 **P99 不稳定**，不得下结论。
- 建议先热机／预热至少 30–60 秒（按实际采集和工况），之后每个独立场景记录至少 300 帧；持续测试至少 600 帧或 10 分钟，以时间较长者为准。记录单线程／线程池、相机实时率、输出限速与高负载场景。
- `observed_loop_hz` 包含可能存在的速率节流或日志 I/O；不能当作无限速算力。若前台停顿、后台热降频或 SD 卡 I/O 占满，应把这一轮结果标记为受干扰。
- **性能门槛不代替正确性门槛**：一旦 UART 字节、姿态/目标有效性、独立物块数量产生非预期变化，就不能仅凭加速接受修改。
- 典型 15 目标实机目标保持 5–6 Hz；是否达到以真实完整流数据证明。不预设 r41 整机 FPS 会提升 20%。同条件若 P95 时间回退超过 10%，须定位后再决定；单次测量不触发自动回滚。
- 若系统实测在 `~/.local/share/jetson-chat-dev` 无权限或项目依赖欠缺，仅记录不可测条件，不额外修改系统 Python/CUDA/OpenNI/模型路径。

## 4. 已准备的命令（**不是现在执行的指令**）

仅在本机离线验证：

```bash
python3 tools/r41_preflight.py --tier quick --baseline-root /path/to/r40 --output /tmp/r41_quick.json
python3 tools/r41_preflight.py --tier full --baseline-root /path/to/r40 --output /tmp/r41_full.json
```

独立目录中仅做工具链检查（不运行相机或推理）：

```bash
python3 tools/r41_device_readiness.py --output /tmp/r41_device_readiness.json
```

从**已存在的应用日志**统计帧时延与对象数分布：

```bash
python3 tools/r41_runtime_report.py --frames /path/to/frames.jsonl --summary /path/to/run_summary.json --warmup 30 --output /tmp/r41_runtime_report.json
```

从**已经采集的 tegrastats 输出文件**统计温度、GPU、RAM、板级功耗（不主动开启采样）：

```bash
python3 tools/r41_tegrastats_report.py --log /path/to/tegrastats.log --interval-ms 1000 --output /tmp/r41_thermal_report.json
```

对同一场景的原始 PNG 做不改色对照：

```bash
python3 tools/r41_color_diagnostic.py --normal /path/normal1.png /path/normal2.png --suspect /path/green1.png /path/gray1.png --roi 180 250 200 100 --output /tmp/r41_color_report.json
```

注意：这两类日志分析**不等于主动监控程序**，不会把图片、模型或设备秘密上传至公开 GitHub。

## 5. 发布次序与硬约束

1. 锁定受审查的 Git SHA、保存原有动态库哈希和回退点。
2. 验证代理升级脚本在旧 Git/Python3.6 下所有测试通过；不依赖无效 HEAD、网络临时成功或空目录的假通过。
3. 仅在独立工作区构建和运行实机测试；再确认检测准确性、UART、时序和产物 ABI。
4. 对比相同场景的 r40/r41 原生内核和完整系统表现；**结果可重复**才能形成收益结论。
5. 生产服务替换、真正的硬件串口联调、开启真实相机或改变电源模式**单独确认**；没有该确认不执行。

本轮只准备脚本与测试，不会执行上述 Jetson 步骤。不存在“万无一失”的软件保证，实际目标是通过可重复验收、预检、最小权限与回退把误操作和假结果风险降到可控范围。
